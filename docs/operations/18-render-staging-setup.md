## 1. Audit of the current setup

| Area | Finding | Consequence for staging |
|---|---|---|
| Build | `pnpm install --frozen-lockfile` → `prisma generate` (client is not committed) → `next build`. Node ≥ 24.14 (`engines`), pnpm 11.9.0 (`packageManager`, through corepack). | Same build command on Render. `NODE_VERSION=24.14.0` pins Node. |
| Web | `next start` serves the app. `/health/live` reports the process is up. `/health/ready` checks the database, migrations (including `EXPECTED_DATABASE_MIGRATION`), and email/AI configuration. | Health check on `/health/ready`. A deploy never goes live if migrations are missing. |
| Public env | `NEXT_PUBLIC_APP_URL` is compiled into the client bundle at build time. | Changing it needs a new build, not just a restart. |
| Database | Prisma 7 + PostgreSQL. CI runs 16. 14 migrations, all additive apart from two `DROP INDEX` replaced by unique indexes (no data loss). | Postgres **16** to match CI and local. `prisma migrate deploy` runs in the pre-deploy step. |
| Worker | `pnpm worker` runs a long poll loop over durable DB jobs, with fenced leases, a 30 s heartbeat in `WorkerHeartbeat` and graceful drain on SIGTERM. | It needs its **own background worker service**. It cannot run inside the web process. It is not run on demand. |
| Maintenance | `pnpm maintenance` runs a one-shot batch that expires exports, reservations and leases and prunes reset tokens, rate-limit buckets and stale heartbeats. | Hourly **cron job**. |
| Queues / cache | No Redis, Key Value, object storage or external queue. Jobs, rate limits and sessions live in PostgreSQL. Exports are generated on request. | Nothing else to provision. |
| AI | The gateway routes to `MOCK` by default. The env schema **rejects** `AI_REAL_GENERATION_ENABLED=true` when `APP_ENV=staging`. Local runtimes (Ollama/MLX) are evaluation-only. | Staging is mock-only for AI. No AI provider is added. A real-AI smoke (A-17) needs a separate approved change. Gateway compatibility is unchanged. |
| Email | SMTP through `mail.webcontentflow.com:587` with STARTTLS (ADR-078). | SMTP credentials are entered in the Dashboard. |
| Secrets | None in the repository (`pnpm security:secrets` runs in CI). | `AUTH_SECRET` and `RATE_LIMIT_SECRET` are generated by Render. SMTP credentials are entered by hand. |

1. **Review and merge** the PR that contains this guide (CI green).
2. **(owner)** In Render: **New → Blueprint**, repository `pixart-web/web-content-flow`, branch `main`. Render shows the four resources and the environment group from section 2. Check the plans and the region before you confirm.
3. **(owner)** Fill the prompted values: `SMTP_USER` and `SMTP_PASSWORD` (web, worker, cron) and `APP_RELEASE` (web, worker; for example `7f6713f`). The secrets are generated, and worker/cron copy them from web automatically.
4. **(owner)** Confirm the Blueprint. Render creates the database, then builds. The web pre-deploy step runs the migration guard and `prisma migrate deploy` against the empty database (14 migrations). Never seed staging.
5. **(owner)** Mail host and DNS: follow sections 3 and 4 of [13-staging-deployment-checklist.md](13-staging-deployment-checklist.md). Then add the CNAME `app-staging` → the `*.onrender.com` host Render shows, and wait for the TLS certificate.
6. Tell Claude, who runs the smoke checklist (section 8) and records the evidence.

## 6. Routine deploy

1. Merge to `main` with CI green.
2. **(owner)** Note the current live commit of each service (Render → Events) as the rollback target.
3. **(owner)** Deploy **web** first with **Manual Deploy → Deploy latest commit**. Its pre-deploy step applies migrations before any process uses them. A failed pre-deploy keeps the previous version live.
4. After `/health/ready` is 200, deploy **worker** and then **cron** with the same commit.
5. Update `APP_RELEASE` if you track it, and run the short smoke checks (8.1).

Web and worker must run compatible commits. Deploy them within the same session.

## 7. Migrations: safety rules

- `pnpm migrate:production` runs `pnpm migrate:check` and then `prisma migrate deploy`. The check (`scripts/check-migration-safety.ts`) **blocks the deploy** if any migration contains `DROP TABLE/COLUMN/SCHEMA/TYPE`, `TRUNCATE`, `DELETE FROM`, a column type change or a `RENAME`, unless the file contains a reviewed marker `-- destructive-approved: <who> <date> <reason>`. CI runs the same check.
- `prisma migrate deploy` only applies committed migrations, in order. It never resets or generates SQL. `migrate dev`, `db push` and `migrate reset` are never used against staging.
- New migrations stay **additive** (nullable columns, new tables, new indexes). Removals follow expand → migrate → contract across separate releases.
- The irreversible ADR-070 enum step is **not** part of this setup and needs its own approval.

## 8. Smoke checklist

### 8.1 After every deploy (≈ 5 min)

- [ ] `curl -sI https://app-staging.webcontentflow.com/health/live` returns `200`.
- [ ] `curl -s https://app-staging.webcontentflow.com/health/ready` returns `200` with `"migrations":"ok"`, `"email":"configured"`, `"ai":"disabled"`.
- [ ] The response headers include `X-Robots-Tag: noindex, nofollow`, and `/robots.txt` disallows everything.
- [ ] The worker log shows `{"event":"worker.heartbeat","state":"running"}` within 60 s.
- [ ] Sign in with an invited test account and open the dashboard.

### 8.2 First deploy (full)

- [ ] The registration page is closed. Capture mode is not reachable.
- [ ] Mock generation for each module: Brief → Brand Profile → Website, Social, Ads, Video, Copy, Calendar. Jobs reach `COMPLETED` on the worker.
- [ ] Restart the worker during a job. The lease is recovered and nothing is duplicated.
- [ ] Trigger the cron manually (**Trigger Run**). The log shows `maintenance.completed`.
- [ ] Password recovery to a controlled inbox: the message arrives, the headers show SPF and DKIM pass, and the link works only once.
- [ ] Export: one item in each format, plus a project package.
- [ ] The database shows a backup and the PITR window. Run `pnpm restore:verify` against an isolated restore ([03-backup-and-restore.md](03-backup-and-restore.md)).
- [ ] The full package in [15-staging-smoke-test-package.md](15-staging-smoke-test-package.md). Record everything in [14-staging-evidence-record.md](14-staging-evidence-record.md).

## 9. Rollback

| Failure | Action |
|---|---|
| Build or pre-deploy fails | Nothing to do. The previous version stays live. Fix forward. |
| The new web version is unhealthy | Render keeps the old instance while the health check fails. If it went live and misbehaves, use **Rollback** on the web service (Events → previous deploy). |
| Web works, worker misbehaves | Roll back the worker to the commit that matches the web version. Leases expire and jobs are retried. |
| A migration was applied and the new code is bad | Roll back the code only. Migrations are additive, so the previous code keeps working with the newer schema. Do **not** reverse the migration. Fix forward with a new migration if needed. |
| Data corruption | Stop the worker and cron (Suspend). Restore from PITR to a **new** database, verify it, then point `DATABASE_URL` at it ([03-backup-and-restore.md](03-backup-and-restore.md)). Only with the owner's approval. |
| Disable a feature without deploying | Use the flags `ROLLOUT_STATE=MAINTENANCE`, `EXPORTS_ENABLED=false` and `PROJECT_PACKAGE_EXPORT_ENABLED=false` in the environment group, then restart. |

Rehearse one web rollback and one worker rollback on staging before the beta, and record them in [11-rollback-rehearsal.md](11-rollback-rehearsal.md).
